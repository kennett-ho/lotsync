# Production Migration Rehearsal — Sprint 07 Record

**Executed:** 2026-08-16, entirely against disposable local
infrastructure. **Production was not touched** — not read, not
written, not configured. This document is the evidence record the
Sprint 06 plan required before any real cutover can be scheduled:
the runbook's Release B + Release C sequence was executed end-to-end
against a production-shaped synthetic environment, validated, broken
on purpose, and rolled back on purpose.

**Verdict: PASS** — with the findings below folded back into the
tools and runbook. See "Go/No-Go" at the end.

**Structural** — 13 tables, 14 indexes, schema_migrations 1..9, FKs
enforced through the copy itself, every identity sequence ≥ MAX(id):
all ok.
**Counts** — all 12 business tables exactly equal source: ok.
**Domain invariants** — every status/type breakdown, distinct-VIN
count, all four orphan checks, min/max of five timestamp columns:
exactly equal.
**Representative rows** — 11 sampled VINs (vehicle row + full event
and task histories) + all sync_run rows + all pending_identity rows:

**Behavioral** (`tools/behavior_compare.py`) — the app's own query

projections (work-order input), recommendations, pending identities,
sync history, all four dashboard aggregates, 10 vehicle details, and

**Validation catches real divergence (proven, not assumed):** with

in a migration comment) — fixed, re-run, then green.

## 8. First PostgreSQL write (the point of no return, simulated deliberately)

A three-vehicle RecovR CSV posted by the admin through the real
endpoint — the exact shape of the supervised first production sync:

- **Delta that exists only in PostgreSQL afterward:** sync_run **13**
  (recovr, complete, 3 records) · events **8930–8932**
  (recovr_observed) · tasks **335, 336** Reality-discharged
  outstanding→**honored** (install_recovr_device) · one vehicle
  recovr_status not_paired→paired.
- **What a raw revert to the frozen SQLite loses:** exactly that — one
  sync run, three events, two honored install records, one status.
  Operationally: two completed RecovR installs would reappear as
  outstanding work.
- Server-side sync time: 29 ms.

## 9. Rollback drill — pre-write (the easy path, proven)

Full revert in one move: stop → SQLite env restored, all auth env
removed → start.

- stop → healthy-on-SQLite: **19.4 s**; tokenless requests 200 again
  (auth revert proven); counts exactly pre-cutover (1,197 / 365 / 12
  — sync 13 absent).
- **Zero loss proven two ways:** the live SQLite file was
  byte-identical to its pre-cutover source (the PostgreSQL-era app
  never wrote it), and logically identical (full ordered-content
  digest) to the final backup.
- **Runbook correction from this drill:** post-rollback verification
  must be *logical* comparison (counts + content digest). Byte-hash
  against the online backup is the wrong test — SQLite's online
  backup is logically identical but not byte-identical to its source
  (page layout/counters differ). The runbook now says so.

## 10. Post-write recovery (the hard path, demonstrated)

After rolling back to SQLite, the same RecovR CSV was replayed
through the same endpoint: SQLite produced **sync_run 13, events
8930–8932, tasks 335/336 honored — identical rows with identical
IDs** (ID allocation converges because both engines continue from the
same preserved sequence high-water). Replay of the day's source
reports is therefore a real, convergent recovery mechanism, not a
hand-wave — bounded by the operator having the source CSVs (they are
staged per-run under `LOTSYNC_API_UPLOADS_DIR` on the disk, plus
whatever the sources re-export). Recovery cost: milliseconds per
sync + the operator effort to gather and re-upload; call it minutes
per lost sync batch, not hours.

## 11. Failure injection (5 scenarios, all fail closed)

| # | Injection | Behavior | Operator move |
|---|---|---|---|
| 1 | Wrong DSN (unreachable port) | Tool: `REFUSED … ConnectionTimeout` exit 3 in 11 s. **Found a real defect first**: no connect timeout → indefinite hang; fixed (`connect_timeout=10`), re-proven | Fix DSN, nothing happened |
| 2 | Divergent/tampered destination | `--validate-only` exit 2, 14 explicit failures | NO-GO; wipe + re-run or abort |
| 3 | Migration interrupted mid-copy | Copy is one transaction → rollback to empty tables → plain re-run works; any *committed* partial state hits the non-empty refusal (exit 3, message names the counts) → `--wipe-destination` re-run (proven) | Re-run; wipe only if refused |
| 4 | `AUTH_MODE=required` without key source | `/health` stays 200; protected routes 500 with the exact cause: "needs SUPABASE_URL or AUTH_JWKS" | Env revert (or supply the var) |
| 5 | Engine flipped to unreachable database | `/health` 500 after **15 s** (pool fails visibly, never hangs) | Env revert to SQLite per runbook |

A sixth defect was found by the tool's own test suite: an
unanswerable production-confirmation prompt crashed with a traceback
instead of refusing cleanly — fixed (EOF → clean exit-3 refusal).

## 13. Migration-tool capabilities, safety gates, tests

Capabilities: dry-run default · `--execute` · `--validate-only` ·
`--wipe-destination` recovery · FK-safe ordered copy with verbatim
IDs · sequence reset to `max(sqlite_seq, MAX(id))` · four-layer exact
validation · JSON report · per-stage timings.
Safety gates: DSN only via env var (never CLI, never printed) ·
read-only source open + integrity + **schema v9 exact** gate ·
non-local destination requires flag + typed interactive phrase,
checked before any connection · non-empty destination refused ·
post-schema emptiness re-check · non-zero exits (2 validation /
3 refusal).
Tests: `tests/test_migration_tool.py` — 10 tests: happy path with
exact counts + ID preservation, sparse-sequence continuation (next
IDs = high-water + 1), dry-run writes nothing, non-empty refusal +
wipe recovery, tampered-destination validation failure, malformed
and missing source refusals, remote-destination ceremony refusals,
missing-DSN refusal, generator determinism. Run under the existing
PostgreSQL CI job via discovery (schema-isolated per test);
self-skip under SQLite. Suite totals: **464/464 both engines** (the
SQLite job additionally skips these 10 by design).

**CI split (deliberate):** CI proves the tool's contract on the
small deterministic fixture every push; the full ~4,700-vehicle
rehearsal is an operator procedure (this record), re-runnable any
time with the three committed tools. No CI workflow changes were
needed or made.

## 14. Runbook/plan changes made from rehearsal evidence

1. B.7/rollback verification: logical content comparison, not
   byte-hash vs the online backup (§9 above).
2. Timing table updated with measured evidence; window kept at 90
   min, expected active ≈30 min.
3. Interrupted-import recovery clarified: transactional copy means
   plain re-run after a mid-copy failure; `--wipe-destination` for
   any committed partial state.
4. Tool hardening recorded: destination connect timeout; clean
   refusal on unanswerable production prompt.
5. Marked **REHEARSED / MEASURED / VALIDATED** annotations on the
   runbook's Release B/C steps; open items marked UNRESOLVED
   (unchanged decision-register entries).

## 15. Rehearsal environment restore / teardown

The standing DealerDOH DEV environment was **never part of this
rehearsal** — no rehearsal component was ever configured with the dev
Supabase project's DSN or credentials (they are not present on this
machine at all), the QA dealership was untouched, and dev `/health`
remained green throughout. Nothing to restore.

Local disposable pieces (all outside the repo, under
`~/Desktop/dealerdoh-rehearsal/`): portable PostgreSQL 17.5 + private
cluster, synthetic datasets/backups, token/JWKS files, logs. The
server is stopped after the rehearsal
(`pgsql/bin/pg_ctl -D pgdata stop`); the directory is kept until the
sprint PR merges (re-running any rehearsal step needs only
`pg_ctl start`), then can be deleted wholesale.

## 16. Go/No-Go assessment

**GO — the production migration is technically ready to schedule** (not
scheduled — that is gate G3, an owner decision), on this evidence:
the runbook executed end-to-end without improvisation; validation
demonstrably catches divergence; both rollback classes behaved as
documented (pre-write: zero-loss env revert; post-write: convergent
replay recovery); five injected failures each produced a clear stop
signal and a documented operator move; and every defect found was in
the rehearsal's own new tooling (parser false-positive, missing
connect timeout, prompt EOF crash, synthetic-data infidelity) — each
fixed and re-proven within the rehearsal. Remaining prerequisites
before G3 are decisions and provisioning, not engineering: the plan
§22 decision register (window date, first-account roster, canonical
IDs, service plans) and the G1 creation of `dealerdoh-prod`.
